## ISSUE-005 — `에 대한`이 변수명에 남는다 (Critical)

### 근본 원인 — 치환 순서가 뒤집혀 있다

`app/survey-research-intent.ts:134-149` `cleanVariableLabel`:

```ts
const cleaned = normalize(value)
  .replace(/^(?:그리고|또한|그에\s*따른|...)\s*/, "")
  .replace(/(?:에\s*대해(?:서)?|에\s*관해(?:서)?|을|를)\s*$/, "")   // ← ①
  .replace(/(?:의)?\s*(?:관계|상관관계|영향|차이)\s*$/, "")          // ← ②
```

입력: `지각 비율에 대한 관계`

1. ①이 먼저 돈다. 문자열 끝이 `관계`라 아무것도 안 지움
2. ②가 `관계`를 지운다 → `지각 비율에 대한`
3. **①은 이미 지나갔다.** 노출된 `에 대한`을 지울 기회가 없다

결과: `지각 비율에 대한`

### 두 번째 결함이 겹친다

①의 정규식은 `에 대해` / `에 관해`(부사형)만 알고 `에 대한` / `에 관한`(관형사형)은 모른다. 순서를 바로잡아도 이 패턴은 여전히 못 잡는다. 두 군데 다 고쳐야 한다.

### 전파 경로

`app/survey-research-intent.ts:219-233` `directVariableName`:

```ts
if (/자취\s*비율/.test(cleaned)) return "현재 거주 형태";   // 특례 있음
...
if (/비율/.test(cleaned)) return cleaned.replace(/\s*비율/, " 여부").trim();  // ← 여기로 떨어짐
```

`지각 비율에 대한` → `지각 여부에 대한`

이 이름이 그대로:
- `researchIntentTitle` → 설문 제목
- `researchIntentDescription` → 안내문
- `researchVariableQuestion` → 문항 2·4·6 본문과 설명

### 대조 실험

`에 대한`을 뺀 프롬프트는 변수명이 깨끗하게 나온다:

```
"대학생들의 통학 시간과 그에 따른 지각 비율 조사"
  → variables: [["통학 시간","grouping"], ["지각 여부","outcome"], ["지각 비율","derived_metric"]]
```

즉 `에 대한` 한 조각이 원인이 맞다.

## ISSUE-006 — generic 이분형 템플릿이 한국어 문장이 아니다 (High)

**변수명을 고쳐도 문항은 여전히 깨진다.** 위 대조 실험의 깨끗한 케이스도 이렇게 나온다:

```
[2] 지각 여부에 해당하나요?
    reason: 지각 여부을(를) 개인별 이분형 변수로 측정함.
```

`app/survey-intent.ts:5260-5268`:

```ts
if (variable.measurementLevel === "binary") {
  return question(
    id,
    `${timeframe}${name}에 해당하나요?`,           // ← 문장이 성립하지 않음
    `${name}을(를) 개인별 이분형 변수로 측정함.`,   // ← "을(를)"이 사용자에게 그대로 보임
    "single",
    ["예", "아니요"],
  );
}
```

두 가지가 잘못됐다:

1. **`${name}에 해당하나요?`는 질문이 아니다.** "지각 여부에 해당하나요?"는 뜻이 통하지 않는다. 이분형 변수를 묻는 자연스러운 형태는 "수업에 지각한 적이 있나요?"다. 템플릿이 변수명을 그대로 조사에 붙이는 구조라 어떤 이름을 넣어도 문장이 안 된다.

2. **조사 하드코딩.** `을(를)`이 화면에 리터럴로 렌더링된다 (스크린샷 확인). 같은 파일 `app/survey-intent.ts:1643`에 받침을 판정하는 `labelWithParticle`이 이미 있는데 이 분기만 안 쓴다. "지각 여부"는 받침이 없으니 "를"이어야 한다.

같은 결함이 이 함수의 다른 generic 분기에도 있다:

| 라인 | 코드 | 문제 |
|------|------|------|
| 5254 | `` `${timeframe}${name}은 어느 구간에 해당하나요?` `` | `은/는` 미판정 |
| 5264 | `` `${name}을(를) 개인별 이분형 변수로 측정함.` `` | `을(를)` 노출 |
| 5277 | `` `${timeframe}${name}은 어느 정도인가요?` `` | `은/는` 미판정 |
| 5278 | `` `${name}을(를) 겹치지 않는 순서형 구간으로 측정함.` `` | `을(를)` 노출 |
| 5285 | `` `${timeframe}${name}은 어느 수준에 해당하나요?` `` | `은/는` 미판정 |
| 5286 | `` `${name}을(를) 비교 가능한 응답 범주로 측정함.` `` | `을(를)` 노출 |

즉 **generic 폴백에 떨어지는 모든 변수**가 이 문제를 겪는다. 특례가 등록된 변수(통학 시간, 수면 시간, 학년, 거주 지역 등)만 멀쩡하다.

## ISSUE-007 — `지각 비율`에 전용 경로가 없다 (Medium)

`자취 비율`과 비교하면 차이가 분명하다:

| | 자취 비율 | 지각 비율 |
|---|---|---|
| `directVariableName` 특례 | ✅ → `현재 거주 형태` | ❌ generic `/비율/` → `지각 여부` |
| `researchVariableQuestion` 전용 문항 | ✅ `현재 거주 형태를 알려주세요.` + 5지선다 | ❌ generic binary 폴백 |
| `relationalIntentBlueprint` 전용 블록 | ✅ `commuteResidence` 분기, 7문항 세트 | ❌ 없음 → generic 분기 |
| 결과 | 정상 설문 | 깨진 문항 |

`지각 비율` / `지각률`은 통학 시간과 함께 쓰이는 대표적인 조합인데(사용자가 실제로 두 번 다 이 조합을 시도했다) 등록되어 있지 않다.

## ISSUE-008 — 설명문 조사 하드코딩 (Medium)

`app/survey-research-intent.ts:433`:

```ts
return `${target}의 ${withAndParticle(left.name)} ${right.name}를 파악하고, ${goal}에 ...`;
                                                              ^^^ 하드코딩
```

바로 위 `withAndParticle`은 받침을 판정해서 `과/와`를 고르는데, `를`은 그냥 붙인다. 결과:

```
대학생의 통학 시간과 지각 여부에 대한를 파악하고, ...
                              ^^^ "한"은 받침이 있으니 "을"이어야 함
```

지금은 ISSUE-005 때문에 드러났지만, 받침으로 끝나는 변수명(`거주 형태`는 무받침이라 우연히 맞음, `성적`·`학년`·`이직 의향` 등은 틀림)이면 언제든 재발한다.

## ISSUE-009 — 문항이 응답자에게 내부 개념을 노출 (Medium)

`app/survey-intent.ts:5322-5327` generic 관계형 분기:

```
[3] 앞에서 답한 첫 번째 값이 달라지는 주된 상황을 모두 골라주세요.
[5] 앞에서 답한 값들이 평소와 달라지는 빈도는 어느 정도인가요?
```

응답자는 "첫 번째 값"이 뭘 가리키는지 모른다. 설문지는 위에서부터 스크롤하며 답하는 물건이라 "앞에서 답한"이 어느 문항인지도 불분명하다. 변수명을 직접 써야 한다 — "통학 시간이 평소와 달라지는 주된 상황".

`commuteResidence` 분기(5300-5304)는 같은 자리에 "통학 시간이 현재 거주 형태를 선택하는 데 어느 정도 영향을 주었나요?"처럼 변수명을 박아 넣는다. generic 분기만 플레이스홀더로 남아 있다.

## 구조적 관찰

`researchVariableQuestion`(`app/survey-intent.ts:5040-5290`)은 25개 남짓의 `if (/변수명/)` 특례를 손으로 나열하고, 매칭이 없으면 generic 템플릿으로 떨어진다. generic 템플릿이 한국어 문장으로 성립하지 않으므로 **특례에 없는 변수는 전부 깨진 문항이 된다.**

앞선 리포트(`qa-report-baroform-code-analysis-2026-08-21.md`)에서 지적한 화이트리스트 문제와 같은 뿌리다. 그때는 검증기 화이트리스트, 이번엔 생성기 화이트리스트다. 특례를 하나씩 추가하는 방식으로는 사용자가 새 변수를 쓸 때마다 재발한다.

generic 템플릿 자체가 어떤 변수명을 받아도 문법적으로 성립하도록 만드는 게 먼저다. `labelWithParticle`을 쓰고, 변수명을 조사에 직접 붙이는 대신 측정 수준별로 자연스러운 문형을 고르는 구조여야 한다.
